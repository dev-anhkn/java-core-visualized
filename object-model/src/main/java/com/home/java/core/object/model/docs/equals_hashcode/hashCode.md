# hashCode trong Java – Bản ngắn gọn nhưng đủ hiểu cốt lõi1. `hashCode()` là gì?    - `hashCode()` là method trả về một số nguyên (`int`) đại diện cho object.    - Nó được khai báo trong `java.lang.Object`:    - `hashCode()` không dùng để nói hai object có bằng nhau hay không.    - Nó chỉ tạo ra một “mã số đại diện” để Java xử lý object nhanh hơn trong một số cấu trúc dữ liệu.2. Bản chất cần nhớ    - `equals()` trả lời câu hỏi: Hai object này có bằng nhau về mặt logic không?    - `hashCode()` trả lời câu hỏi: Hai object này nên được xếp vào “nhóm mã” nào?    - Nói dễ hiểu hơn:        - `equals()` dùng để **kết luận** có bằng nhau hay không        - `hashCode()` dùng để **hỗ trợ tìm nhanh** trước khi so sánh thật sự bằng `equals()`3. `hashCode()` mặc định của `Object`    - Nếu không override, mỗi object sẽ có một hash code mặc định. Object là giá trị do JVM/native runtime tự cấp cho      object, thường mang ý nghĩa nhận diện object theo identity, không theo value.        - mặc định `hashCode()` thường gắn với **identity của object**        - không gắn với **nội dung logic** của object        - JVM tự cấp một hash mặc định gắn với identity của object      ``` java        public native int hashCode();      ```4. Khi nào cần override `hashCode()`?    - Khi bạn đã override `equals()` để so sánh theo nội dung, thì gần như phải override luôn `hashCode()`.    - Vì sao? Vì Java có một rule rất quan trọng: Nếu `a.equals(b) == true` thì `a.hashCode()` phải bằng `b.hashCode()`.5. Rule quan trọng nhất của `hashCode()`    - Nếu hai object **bằng nhau theo `equals()`**, thì **phải có cùng `hashCode()`**.    - Nếu hai object có cùng `hashCode()`, **chưa chắc** chúng bằng nhau.    - Trong lúc dữ liệu object chưa đổi, gọi `hashCode()` nhiều lần phải ra cùng kết quả.6. Vì sao cùng hash code chưa chắc bằng nhau?    - Vì số lượng object là rất lớn, nhưng `int` chỉ có giới hạn giá trị.    - Nên bắt buộc sẽ có trường hợp:        - 2 object khác nhau        - nhưng hash code trùng nhau        - Trường hợp này gọi là **collision**. Điều này là bình thường.        - Nghĩa là:            - `hashCode()` không phải “chứng minh thư tuyệt đối duy nhất”. Nó chỉ là mã hỗ trợ phân loại nhanh.7. Nguyên tắc cực kỳ quan trọng    - Field nào dùng để so sánh trong `equals()` thì cũng phải dùng để tính trong `hashCode()`.8. Mutable object và rủi ro    - Nếu object có field thay đổi được, thì `hashCode()` cũng có thể thay đổi theo.    - Ví dụ:   ``` java   User u = new User("Alice");   int h1 = u.hashCode();      u.name ="Bob";   int h2 = u.hashCode();   ```    - Lúc này `h1` và `h2` có thể khác nhau.    - Điều đó không sai về cú pháp, nhưng rất nguy hiểm về logic.    - Vì vậy:        - object dùng để định nghĩa equality/hash nên ưu tiên **immutable**        - hoặc ít nhất các field tham gia `equals/hashCode` nên ổn định9. Cách hiểu đúng về vai trò của `hashCode()`    - Không nên học `hashCode()` như một method rời rạc.    - Phải hiểu nó đi cùng `equals()` thành một cặp:        - `hashCode()` giúp gom nhanh        - `equals()` giúp xác nhận thật sự    - Tức là:        - `hashCode()` là bước lọc nhanh.        - equals()` là bước kiểm tra cuối cùng.## Cốt lõi cần nhớ sau 1 tháng đọc lại### Chỉ cần nhớ 5 ý này:1. `hashCode()` trả về một số nguyên đại diện cho object.2. Nó không tự quyết định hai object có bằng nhau hay không.3. `equals()` mới là nơi quyết định equality theo logic.4. Nếu 2 object `equals()` nhau thì `hashCode()` phải giống nhau.5. Override `equals()` thì gần như luôn phải override `hashCode()` cùng lúc.## Bản diễn đạt siêu ngắn để nhớ> `hashCode()` không dùng để kết luận “có bằng nhau hay không”.>> Nó chỉ tạo ra mã số để Java xử lý object nhanh hơn.>> `equals()` mới là nơi kết luận cuối cùng.>> Hai object đã được coi là bằng nhau theo `equals()` thì bắt buộc phải có cùng `hashCode()`.
