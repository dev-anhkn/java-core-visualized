# List trong Java## 1. List là gì?- Là 1 interface trong Java Collections Framework, kế thừa từ Collection- Đặc điểm cốt lõi    - có thứ tự (ordered)    - lưu được phần tử trùng lặp    - truy cập phần = index    - mỗi phần tử có một vị trí xác định trong dãy## 2. Bản chất của List- Collection trả lời cho câu "Ta nắm giữ nhiều phần tử", List thêm "Ta giữ nhiều phần tử theo trật tự tuyến tính (  trình tự nối tiếp nhau), mỗi phần tử ở một vị trí cụ thể"- Khi dùng List, ta đang nói: “Tôi cần một dãy phần tử có thứ tự, và vị trí của phần tử là quan trọng.”## 3. List với Collection- Collection là abstraction tổng quát cho "1 nhóm obj"- List là abstraction cho "1 dãy phần tử được sắp xếp theo trình tự"## 4. Contract của List là gì?- List có một số đặc điểm hành vi quan trọng mà mọi implementation phải tuân theo.    - Có thứ tự    - Có index    - Cho phép duplicate    - equals() của List phụ thuộc vào thứ tự + nội dung    - Hai List bằng nhau khi:        - cùng số phần tử        - từng phần tử tương ứng bằng nhau theo equals(), theo đúng thứ tự## 5. Các implementation phổ biến của List- Quan trọng nhất:    - ArrayList    - LinkedList- Ngoài ra còn có:    - Vector (cũ, ít dùng)    - CopyOnWriteArrayList (dùng trong concurrency, để sau)## 6. List là cấu trúc “sequence”(Dãy/Chuỗi) chứ không chỉ là “container”(vật chứa)- Nhiều người nghĩ List chỉ là “cái hộp đựng nhiều phần tử”. Không đủ.- mô hình hoá:    - thứ tự xuất hiện    - trình tự xử lý    - logic trước/sau    - vị trí tương đối giữa các phần tử## 7. List phù hợp khi nào?- Dùng List khi bài toán của bạn cần một trong các yếu tố sau:    - cần giữ thứ tự phần tử    - cần cho phép phần tử trùng nhau    - cần truy cập theo vị trí    - cần xử lý dữ liệu như một chuỗi tuyến tính    - cần chèn/xoá/thay thế theo vị trí    - cần output theo đúng thứ tự đã xác định## 8. Những hiểu lầm phổ biến về List- Hiểu lầm 1: List chỉ là mảng động -> Sai.    - Một số implementation có thể gần với ý tưởng đó, nhưng List bản thân nó là interface abstraction, không phải      “mảng động”.- Hiểu lầm 2: List chỉ khác Set ở chỗ cho phép duplicate -> Chưa đủ.    - Khác biệt lớn hơn là:        - List có thứ tự        - List có index        - List coi position là một phần của mô hình dữ liệu- Hiểu lầm 3: List luôn truy cập index nhanh -> Sai.    - Đó là chuyện của implementation, không phải contract của List.- Hiểu lầm 4: phần tử giống nhau trong List là vô nghĩa -> Sai.    - Nhiều bài toán hoàn toàn cần duplicate:        - log events        - lịch sử thao tác        - danh sách kết quả        - dữ liệu input gốc## 9. So sánh bản chất ArrayList và LinkedListArrayListPhù hợp khi:• đọc nhiều• truy cập theo index nhiều• thêm cuối danh sách nhiều• ít chèn/xóa ở giữaƯu điểm:• đọc theo index rất nhanh• cache-friendly hơn do dữ liệu gần nhau trong memory• thường thực tế nhanh hơn LinkedList trong rất nhiều use caseNhược điểm:• chèn/xóa giữa phải shift phần tử• resize có chi phí copy⸻LinkedListPhù hợp khi:• thường xuyên thêm/xóa ở đầu/cuối• ít truy cập random theo index• thực sự cần mô hình linked structureƯu điểm:• thêm/xóa ở đầu/cuối thuận tiện• không cần resize mảngNhược điểm:• đọc theo index chậm• tốn thêm memory cho node và pointer• locality trong memory kém, CPU cache không tối ưu• nhiều trường hợp ngoài thực tế chậm hơn ArrayList⸻11. Độ phức tạp cần nhớArrayList• get(index) → O(1)• add(element) cuối danh sách → trung bình O(1)• add(index, element) → O(n)• remove(index) → O(n)LinkedList• get(index) → O(n)• addFirst/addLast → thường O(1)• add/remove ở giữa nếu đã có node → tốt• nhưng tìm tới vị trí đó vẫn thường O(n)Lưu ý rất quan trọng:Big-O chỉ cho cái nhìn tổng quát.Trong thực tế, ArrayList thường được ưu tiên hơn LinkedList nhiều hơn người mới học tưởng.⸻12. Vì sao ArrayList thường được dùng mặc định?Vì đa số chương trình:• đọc nhiều hơn sửa giữa danh sách• truy cập theo index nhiều• append cuối danh sách là chủ yếu• không thực sự cần linked structureNgoài ra:• bộ nhớ tốt hơn• CPU cache-friendly hơn• overhead object ít hơnNên quy tắc thực chiến rất hay là:Nếu chưa có lý do rõ ràng, hãy dùng ArrayList.⸻13. Khi nào dùng List?Dùng List khi:a. Cần giữ thứ tự phần tửVí dụ:• danh sách lịch sử thao tác• danh sách comment theo thứ tự thời gian• danh sách các bước xử lýb. Cần truy cập bằng indexVí dụ:• lấy phần tử thứ 5• duyệt UI theo vị trí• phân trangc. Cho phép trùng lặpVí dụ:• đơn hàng có thể chứa nhiều sản phẩm giống nhau• log event có thể lặp• danh sách tên có thể trùng⸻14. Khi nào không nên dùng List?Không nên dùng List nếu mục tiêu chính là:a. Chỉ cần uniquenessDùng Set tốt hơn.Ví dụ:• danh sách email không được trùng• danh sách role không trùng• tag không trùngb. Cần tra cứu bằng keyDùng Map tốt hơn.Ví dụ:• tra user theo id• tra config theo key• tra product theo codec. Cần kiểm tra contains cực nhanh trên dữ liệu lớnList.contains() thường phải duyệt tuần tự.Nếu check tồn tại nhiều lần, Set thường phù hợp hơn.⸻15. Sai lầm phổ biến khi dùng Lista. Dùng List để kiểm tra trùng lặp trên tập dữ liệu lớnif (!list.contains(value)) {list.add(value);}Cách này dễ chậm nếu dữ liệu lớn vì mỗi lần contains() có thể quét cả list.⸻b. Nghĩ rằng LinkedList luôn tốt hơn cho insert/deleteĐây là hiểu nhầm rất phổ biến.Đúng là LinkedList không phải shift mảng như ArrayList, nhưng:• phải đi tìm tới đúng vị trí• mỗi node là object riêng• locality bộ nhớ kémNên nhiều case ArrayList vẫn nhanh hơn.⸻c. Trả về implementation cụ thể thay vì interfaceNên ưu tiên:List<String> names = new ArrayList<>();thay vì:ArrayList<String> names = new ArrayList<>();Vì code nên phụ thuộc vào abstraction (List) chứ không buộc chặt vào implementation.⸻16. List và mutable / immutableMutable ListCó thể thay đổi:List<String> list = new ArrayList<>();list.add("A");list.remove("A");Immutable ListKhông cho sửa:List<String> list = List.of("A", "B", "C");list.add("D"); // UnsupportedOperationExceptionDùng immutable list khi:• muốn dữ liệu an toàn hơn• không muốn object khác sửa ngoài ý muốn• biểu diễn dữ liệu cố định⸻17. List lưu object hay lưu reference?Giống các collection khác trong Java, List với object type thực chất lưu reference.Ví dụ:User u1 = new User("An");User u2 = new User("Bình");List<User> users = new ArrayList<>();users.add(u1);users.add(u2);users không chứa toàn bộ object theo kiểu copy object vào bên trong.Nó chứa reference trỏ tới các object đó.Vì thế:u1.setName("An Update");System.out.println(users.get(0).getName()); // An UpdateDo users.get(0) và u1 cùng trỏ tới một object.Đây là điểm rất quan trọng để hiểu bug mutable object trong collection.⸻18. List và equals()Các method như:• contains()• remove(Object o)• indexOf()thường dựa vào equals().Ví dụ:List<String> list = new ArrayList<>();list.add("A");System.out.println(list.contains(new String("A"))); // trueVì String override equals() theo value.Nếu custom class không override equals() hợp lý, hành vi của List có thể không như mong đợi.Ví dụ:class User {String name;User(String name) { this.name = name; }}List<User> users = new ArrayList<>();users.add(new User("An"));System.out.println(users.contains(new User("An"))); // falseVì đang dùng Object.equals() mặc định, tức so sánh reference.⸻19. Tư duy senior về ListKhi nhìn thấy List, không chỉ nghĩ:“À, đây là danh sách.”Mà phải nghĩ sâu hơn:a. Thứ tự có phải là một phần business meaning không?Nếu có, List hợp lý.b. Dữ liệu có cho phép trùng không?Nếu không cho trùng, có thể Set đúng hơn.c. Ta chủ yếu đọc theo index hay tra cứu theo key?Nếu tra cứu nhiều theo key, nên nghĩ tới Map.d. Cần implementation nào?• mặc định: ArrayList• chỉ dùng LinkedList khi thật sự có lý do rõe. Dữ liệu có cần immutable không?• nếu không muốn bị sửa: trả về immutable list hoặc defensive copy⸻20. Rule of thumb thực chiếnHãy dùng ArrayList khi:• chưa chắc dùng gì• cần danh sách có thứ tự• truy cập nhiều• thêm cuối nhiềuHãy cân nhắc LinkedList khi:• thường xuyên thao tác ở đầu/cuối• không cần random access• thật sự hiểu trade-off của nóHãy không dùng List khi:• cần uniqueness → Set• cần lookup theo key → Map⸻21. Ví dụ tổng hợpVí dụ 1: Danh sách tên học viênList<String> students = new ArrayList<>();students.add("Lan");students.add("Hà");students.add("Lan");Dùng List hợp lý vì:• có thứ tự• có thể trùng tên⸻Ví dụ 2: Danh sách email userList<String> emails = new ArrayList<>();Có thể không hợp lý nếu yêu cầu email không được trùng.Khi đó Set đúng bản chất hơn.⸻Ví dụ 3: Tra user theo idList<User> users = new ArrayList<>();Nếu liên tục phải tìm:find user by idthì List không tối ưu.Map<Long, User> phù hợp hơn.⸻22. Cốt lõi phải nhớMột câu định nghĩaList là collection có thứ tự, cho phép duplicate, và truy cập phần tử theo index.Một câu bản chấtDùng List khi vị trí của phần tử có ý nghĩa.Một câu thực chiếnTrong đa số trường hợp, mặc định chọn ArrayList.Một câu cảnh báoĐừng chọn LinkedList chỉ vì nghe nói insert/delete nhanh hơn.⸻23. Mini checklist khi chọn ListTrước khi dùng, tự hỏi:1. Tôi có cần giữ thứ tự không?2. Tôi có cần phần tử trùng nhau không?3. Tôi có cần truy cập theo index không?4. Tôi dùng chủ yếu để đọc, thêm cuối, hay chèn giữa?5. Có phải Set hoặc Map mới là cấu trúc đúng hơn không?⸻Nếu muốn, phần tiếp theo tôi sẽ viết tiếp đúng cùng style này cho ArrayList chuyên sâu riêng một note, rồi sau đó tớiLinkedList chuyên sâu riêng một note.
